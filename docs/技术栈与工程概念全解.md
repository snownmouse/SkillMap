## 二、前端技术选型

### 2.1 React 19 + TypeScript

| 项 | 说明 |
|----|------|
| **React 19** | 最新主版本，支持 Server Components、改进的 Hooks、自动批处理 |
| **为什么选 React** | 生态最大、社区最活跃、组件化开发模式天然适合技能树这种复杂 UI |
| **为什么加 TypeScript** | 200+ 源文件的大型项目必须有类型约束——接口变更时编译器立刻报错，防止运行时崩 |
| **答辩话术** | "全栈 TypeScript——前端 React 19 + TS，后端 Node.js + TS，类型定义在 `src/types/` 下前后端共享。这意味着前端调后端 API 时，如果字段名写错了，编译阶段就能发现，不用等到运行时在浏览器控制台看报错。" |

### 2.2 Vite（构建工具）

| 项 | 说明 |
|----|------|
| **是什么** | 新一代前端构建工具，基于浏览器原生 ES Module，开发时秒级热更新 |
| **为什么不用 Webpack** | Webpack 冷启动慢（大型项目 30 秒+），Vite 冷启动 < 1 秒，HMR 热更新毫秒级 |
| **实际配置** | 开发模式 Express 挂载 Vite 中间件；生产模式 `vite build` 出 `dist/` 静态文件 |
| **答辩话术** | "Vite 的开发体验远超 Webpack——修改一行代码，浏览器几乎瞬间刷新。这在开发技能树可视化这种需要反复调 UI 的场景下特别重要。生产构建用 Rollup，Tree-shaking 效果好，打包体积小。" |

### 2.3 Tailwind CSS v4

| 项 | 说明 |
|----|------|
| **是什么** | 原子化 CSS 框架——不用写 CSS 文件，直接在 HTML 上用 class 控制样式 |
| **为什么选** | 没有样式命名冲突、不需要切文件写 CSS、v4 支持 `@tailwindcss/vite` 插件，零配置 |
| **答辩话术** | "传统 CSS 最大的问题是命名冲突和样式散落。Tailwind 的原子化方案相当于把样式'内联化但标准化'——`bg-blue-500` 永远就是那个蓝色。200+ 组件不会出现'我的 red 覆盖了你的 red'这种问题。" |

### 2.4 Cytoscape.js（图可视化引擎）

| 项 | 说明 |
|----|------|
| **是什么** | 专业的图/网络可视化库，用于渲染节点和边构成的拓扑结构 |
| **为什么选它** | 技能树的本质是**有向无环图（DAG）**，不是树。Cytoscape 原生支持图布局算法（Breadthfirst、CoSE 力导向布局），支持节点拖拽、缩放、点击交互 |
| **为什么不用 D3.js** | D3 更底层，需要手写大量布局逻辑；Cytoscape 自带布局引擎和交互 API，开发效率高 3-5 倍 |
| **答辩话术** | "技能树不是文件目录树，是图——一个节点可能有多个前置依赖。Cytoscape 是目前学术界和工业界最成熟的图可视化方案，也是生物信息学领域做基因网络图的标准工具。我们用它的 Breadthfirst 布局让技能依赖方向清晰可见。" |

### 2.5 Motion（动画库）

| 项 | 说明 |
|----|------|
| **是什么** | 原名 Framer Motion，React 动画库，声明式 API |
| **为什么选** | 技能树生成过程中需要流畅的动画过渡——节点渐入、进度条动画、卡片弹出等 |
| **答辩话术** | "动画不只是好看——它给用户一个'系统正在工作'的心理暗示。生成技能树需要等几十秒，如果没有动画过渡直接'刷'出来，体验很差。Motion 让我们用声明式代码写出流畅动画。" |

### 2.6 React Router v7

| 项 | 说明 |
|----|------|
| **是什么** | React 官方推荐的路由库 |
| **为什么选 v7** | 最新版本，支持数据加载、懒路由、类型安全 |
| **答辩话术** | "路由设计上，我们的核心页面——首页、生成页、技能树页、时间线页——每个都是独立路由。这保证了前进后退、分享链接、浏览器收藏的可用性。" |

## 三、后端技术选型

### 3.1 Node.js + Express + TypeScript

| 项 | 说明 |
|----|------|
| **为什么是 Node.js** | 前后端同语言（TypeScript），类型共享，一个人能写全栈 |
| **为什么是 Express** | 最成熟的 Node.js Web 框架，中间件生态丰富，适合 API 服务 |
| **为什么不选 Next.js/Nuxt** | 项目核心是 API 服务 + SPA 前端，不是 SSR 内容站。Express 更轻量、更灵活 |
| **答辩话术** | "前后端统一 TypeScript 是我们最重要的工程决策之一。`src/types/` 下的类型定义前后端共享——后端 Controller 返回的数据结构和前端 `apiClient.ts` 期望的数据结构由同一份类型保证。这消除了前后端联调中最常见的 bug——字段名不一致。" |

### 3.2 分层架构（Controller → Service → Repository）

| 层 | 职责 | 数量 | 举例 |
|----|------|:--:|------|
| **Controller** | 处理 HTTP 请求/响应，参数校验，调用 Service | 8 个 | `treeController.ts` 处理生成、查询、导入导出 |
| **Service** | 核心业务逻辑，跨多个 Repository 编排 | 18+ 个 | `GrowthPathPlanner.ts` 路径评分算法 |
| **Repository** | 数据库访问封装，只做 CRUD | 4 个 | `TreeRepository.ts` 技能树的增删改查 |
| **Middleware** | 请求预处理——安全、限流、日志、追踪 | 6 个 | `security.ts` 三层防护 |

**答辩话术**："三层架构是后端工程的经典模式。Controller 不写 SQL，Repository 不写业务逻辑，Service 不碰 HTTP 请求对象。每层职责单一，测试时可以分别 Mock——比如测 Service 时可以 Mock Repository 返回假数据。"

### 3.3 LLM 适配层（Provider Pattern）

```
                    ┌─────────────────┐
                    │   LLMService     │  ← 统一入口，负责重试 + 日志
                    └────────┬────────┘
                             │
                ┌────────────┼────────────┐
                ▼            ▼            ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ArkProvider│ │DeepSeek  │ │Gemini    │ ...
        └──────────┘ └──────────┘ └──────────┘
        都实现 ILLMProvider 接口：chat() / chatStream()
```

| 概念 | 说明 |
|------|------|
| **Provider Pattern** | 定义统一接口，不同实现可以互相替换，业务代码不感知底层差异 |
| **为什么需要** | 不同模型的 API 格式不同（Gemini 用 Google GenAI SDK，Ark 用 OpenAI 兼容接口） |
| **切换方式** | 改环境变量 `LLM_PROVIDER=deepseek` 即可，零代码改动 |
| **熔断机制** | 主模型调用失败 → 等待 1 秒 → 自动重试一次 → 仍失败则抛错 |

**答辩话术**："这个设计类比手机充电——不管你是 Type-C 还是 Lightning，插座那头是统一的。我们定义了 `ILLMProvider` 接口，每种模型实现这个接口。业务代码只调 `llmService.chat()`，不关心后面是豆包还是 DeepSeek。这让我们可以随时根据成本和效果切换模型。"

### 3.4 WebSocket 服务

| 项 | 说明 |
|----|------|
| **库** | `ws`（Node.js 最轻量的 WebSocket 实现） |
| **消息类型** | `subscribe_task` / `unsubscribe_task` / `task_update` / `progress_update` / `achievement_earned` |
| **认证** | Cookie 会话（`sm_guest`）+ Bearer Token（`auth` 消息）双通道 |
| **安全** | Origin 白名单 + Task 归属校验 + 连接/消息频率限流 + 心跳检测 |
| **跨实例** | Redis PubSub 广播 task_update，多实例部署时所有进程同步 |
| **答辩话术** | "HTTP 是'你问我答'，WebSocket 是'一直保持通话'。技能树生成耗时 30-120 秒，用户提交后如果只能轮询'好了吗好了吗'，体验很差。WebSocket 让服务器能主动推消息给前端——任务进度到 50%、节点生成中、全部完成——每一步前端都能实时感知。" |

## 四、数据存储方案

### 4.1 双数据库自适应

```
NODE_ENV=development → SQLite（better-sqlite3，单文件，零配置）
NODE_ENV=staging|production → PostgreSQL（必须配置，否则启动失败）
```

| 对比维度 | SQLite | PostgreSQL |
|---------|--------|-----------|
| 部署依赖 | 零依赖 | 需要独立数据库服务 |
| 并发能力 | 单写（WAL 模式提升读）| 多连接池，支持高并发 |
| 适用场景 | 本地开发、单机测试 | 生产环境、多实例部署 |
| 切换方式 | 默认 | 设置 `DB_HOST` 环境变量 |

| 关键设计 | 说明 |
|---------|------|
| **SQL Builder 抽象层** | 所有 SQL 方言差异集中在 `sqlBuilder.ts`（如 `$1` vs `?`、`NOW()` vs `CURRENT_TIMESTAMP`），业务代码不写原生 SQL |
| **Pool 适配器** | SQLite 本身不支持 `pool.query()` 模式，我们封装了 `createSqlitePoolAdapter()`，让 SQLite 也能用 `.query(sql, params)` 接口 |
| **答辩话术** | "这个设计在软件工程里叫'接口隔离'——上层业务代码不感知底层是 SQLite 还是 PostgreSQL。开发者本地跑 SQLite 零配置立刻开始写代码；部署时切 PostgreSQL 一行配置解决。两个数据库共享同一套 Controller/Service/Repository 代码。" |

### 4.2 版本化数据库迁移

| 迁移 | 内容 | 关键变更 |
|------|------|---------|
| `0001_initial` | 初始表结构 | trees, chat_messages, users, sessions 等 10+ 表 |
| `0002_guest_sessions` | 访客会话 | guest_sessions 表，HttpOnly Cookie 映射 |
| `0003_tasks_inputs` | 任务输入存储 | tasks 表增加 inputs/user_id 列 |
| `0004_tasks_retry` | 任务重试 | 租约、重试计数、过期标记 |

**答辩话术**："数据库变更是软件工程里最容易出事的环节——'在我机器上能跑'不叫能跑。我们用版本化迁移脚本管理每次 Schema 变更，服务启动自动执行未应用的迁移，支持升级和回滚。`schema_migrations` 表记录已执行的版本号，不会重复执行。"

### 4.3 Redis 的三重角色

| 角色 | 实现 | 用途 |
|------|------|------|
| **消息队列** | Redis Stream + Consumer Group | 任务入队出队，Worker 消费 |
| **跨进程广播** | Redis PubSub | 多实例 WebSocket 同步推送 |
| **限流存储** | `INCR + EXPIRE` | 分布式限流（替代内存 Map）|

**答辩话术**："Redis 在我们的架构里扮演三个角色，但不是必须的——限流有内存降级方案，队列有进程内方案。Redis 的价值在于多实例场景：两个 API 进程需要共享限流计数、两个 Worker 进程不能抢同一个任务——这些都靠 Redis。"

## 五、安全架构（纵深防御）

```
请求到达
    │
    ▼
┌──────────────┐  第 1 层  CORS 白名单 + Body 大小限制
├──────────────┤  第 2 层  安全响应头 (CSP / X-Frame / HSTS)
├──────────────┤  第 3 层  输入清洗 (XSS / Script 标签过滤)
├──────────────┤  第 4 层  限流 (15分钟/100请求，Redis+内存双模式)
├──────────────┤  第 5 层  认证 (Token hash + bcrypt + HttpOnly Cookie)
├──────────────┤  第 6 层  请求追踪 (全局 Trace ID)
└──────────────┘
    │
    ▼
  业务处理
```

| 层 | 安全机制 | 一句话说明 |
|----|---------|-----------|
| 网络层 | CORS 白名单 | 只允许你指定的域名访问 API |
| 传输层 | 安全响应头 | 告诉浏览器"别把我嵌在 iframe 里""只能用 HTTPS" |
| 应用层 | 输入清洗 | 过滤 `<script>`、`onerror=`、`javascript:` 注入 |
| 频率层 | 速率限制 | 一个 IP 15 分钟内最多 100 次请求 |
| 身份层 | Token + Cookie | 你是谁、你凭什么访问这个资源 |
| 审计层 | Trace ID | 出问题时能定位到具体哪次请求 |

**答辩话术**："安全是纵深防御，不是加个登录就安全了。我们做了 6 层——攻击者要绕过 CORS、绕过安全头、绕过清洗、绕过限流、伪造身份、还要不留痕迹——这基本不可能。每层失败都有下一层兜底。"

## 六、部署与运维

### 6.1 Docker Compose 四服务架构

```yaml
services:
  postgres:    # PostgreSQL 16，带健康检查
  redis:       # Redis 7，带健康检查
  app:         # API + HTTP + WebSocket，禁用内置 Worker
  worker:      # 独立 Worker 进程，只消费 Redis Stream
```

| 概念 | 说明 |
|------|------|
| **为什么分离 app 和 worker** | LLM 调用是 CPU/IO 密集型操作，如果和 HTTP 服务同进程会阻塞请求处理 |
| **健康检查** | PostgreSQL 和 Redis 都有 `healthcheck` 配置，app/worker 的 `depends_on` 确保依赖就绪后才启动 |
| **数据持久化** | PostgreSQL 数据挂载到 Docker Volume `pgdata`，容器重启不丢数据 |

**答辩话术**："`docker compose up --build` 一行命令启动 4 个服务——数据库、缓存、API、Worker 全部就绪。app 和 worker 用同一个 Dockerfile，通过不同 `command` 区分角色。这是生产级的部署方案，不是 demo 级的。" 

### 6.2 CI/CD + PM2

| 工具 | 用途 |
|------|------|
| **GitHub Actions** (`.github/workflows/ci.yml`) | 代码推送自动触发 lint + test |
| **PM2** (`ecosystem.config.cjs`) | Node.js 进程管理，支持集群模式、自动重启、日志管理 |
| **Nginx** | 生产反代——SSL 终端、静态资源缓存、负载均衡 |

### 6.3 优雅关闭（Graceful Shutdown）

`server.ts` 监听 `SIGTERM` 和 `SIGINT` 信号：
1. 停止指标自动快照
2. 停止告警周期检查
3. 停止任务重试调度器
4. 停止 Worker
5. 关闭 WebSocket（通知所有连接客户端）
6. 关闭 HTTP 服务器
7. 关闭数据库连接池
8. 10 秒超时强制退出

**答辩话术**："部署时直接 kill 进程会导致任务丢失、连接断开。优雅关闭保证了：正在处理的任务要么完成要么标记失败，WebSocket 客户端收到关闭通知，数据库连接正常释放。这是生产环境的基本素养。"

## 七、关键工程概念速查

### 7.1 进程与架构

| 概念 | 一句话 | 项目中的体现 |
|------|--------|------------|
| **单体仓库（Monorepo）** | 前后端代码在同一个 Git 仓库里 | 前端 `src/components/`，后端 `src/server/` |
| **一体化架构** | 开发时一个进程同时提供 API 和静态文件 | `server.ts` 挂载 Vite 中间件 |
| **进程分离** | 生产时 API 和 Worker 跑在不同进程中 | `docker-compose.yml` 两个 service |
| **SPA（单页应用）** | 前端只有一个 HTML 页面，路由切换不刷新浏览器 | React Router v7 客户端路由 |
| **SSR（服务端渲染）** | 在服务器上先把 React 渲染成 HTML，再发给浏览器 | 预留 `entry-server.tsx`，暂未启用 |

### 7.2 通信模式

| 概念 | 一句话 | 项目中的体现 |
|------|--------|------------|
| **REST API** | URL 表示资源，HTTP 方法表示操作（GET 读/POST 创建/PUT 修改/DELETE 删除） | 30+ 个 API 端点 |
| **WebSocket** | TCP 长连接，双向全双工通信 | `/ws` 端点，支持订阅/推送 |
| **轮询（Polling）** | 前端定时发请求"好了没？好了没？" | `GET /api/trees/task/:taskId` 兜底机制 |
| **PubSub（发布订阅）** | 发布者发消息，所有订阅者都收到 | Redis PubSub 跨进程 WebSocket 广播 |
| **消息队列** | 生产者放消息，消费者排队处理 | Redis Stream + Consumer Group |

### 7.3 分布式系统

| 概念 | 一句话 | 项目中的体现 |
|------|--------|------------|
| **租约（Lease）** | "这个任务归我处理，有效期 X 秒，过期自动释放" | `tasks` 表的 `lease_id` + `lease_expires_at` |
| **幂等性** | 同一个操作执行 1 次和 100 次结果一样 | 租约确保一个任务不会被两个 Worker 重复执行 |
| **指数退避** | 重试间隔越来越长（1s → 2s → 4s → 8s） | 任务自动重试策略 |
| **熔断（Circuit Breaker）** | 下游服务挂了，快速失败而不是一直等 | LLM Provider 切换 |
| **心跳（Heartbeat）** | 定时 ping/pong 检测连接是否还活着 | WebSocket 30 秒心跳 |

### 7.4 数据库

| 概念 | 一句话 | 项目中的体现 |
|------|--------|------------|
| **迁移（Migration）** | 数据库 Schema 变更的版本管理 | `src/server/migrations/` 4 个迁移脚本 |
| **WAL 模式** | SQLite 的写前日志，允许同时读写 | `db.pragma('journal_mode = WAL')` |
| **连接池** | 预先创建 N 个数据库连接，用完归还，避免反复创建销毁 | PostgreSQL `max: 20` |
| **外键约束** | 子表的记录必须对应父表存在的记录 | `FOREIGN KEY (tree_id) REFERENCES trees(id) ON DELETE CASCADE` |
| **索引** | 加速查询的数据结构，空间换时间 | 20+ 个索引，覆盖高频查询列 |

## 十、答辩高频技术问题

### Q1："为什么不用 Python/Django 做后端？"
> "我们的核心优势之一是全栈 TypeScript——前后端共享类型定义，一个人能高效完成全栈开发。如果用 Python，需要在 TypeScript 和 Python 之间维护两套类型定义，或者靠 API 文档手写类型，效率低且容易出错。另外 Node.js 的异步 IO 模型天然适合我们这个场景——大量时间花在等待 LLM 返回，而不是 CPU 计算。"

### Q2："Express 太老了，为什么不用 Fastify/Koa？"
> "Express 的生态最成熟——几乎所有 Node.js 中间件都有 Express 版本。而且我们这个项目中间件层不重，Express 的性能瓶颈不在这里——真正的瓶颈在 LLM 调用，那是 30-120 秒的级别，Express 毫秒级的开销可以忽略。"

### Q3："SQLite 能撑住生产环境吗？"
> "SQLite 不适合多用户高并发生产环境——所以我们设计了自动切换机制。本地开发用 SQLite 零配置，部署时检测到 `NODE_ENV=production` 自动要求 PostgreSQL。切换对业务代码透明，不需要改一行代码。"

### Q4："JSON 修复是你自己写的还是用的开源库？"
> "核心修复逻辑是自研的——因为 LLM 的 JSON 错误模式比较特殊，不是标准库能覆盖的（比如截断在字符串中间、中文引号干扰、括号不配对）。我们的 `smartFixJson()` 方法经过大量实际 LLM 输出调优，有 10 步修复流水线。同时我们也在代码中使用了标准的 JSON.parse 和正则匹配作为 fallback。"

### Q5："这么多 LLM Provider，切换真的零代码吗？"
> "是的。所有 Provider 实现同一个 `ILLMProvider` 接口——`chat()` 和 `chatStream()` 两个方法。环境变量 `LLM_PROVIDER=deepseek` 决定初始化哪个实例。业务代码只调 `llmService.chat(messages)`，不关心后面是豆包还是 DeepSeek。"

### Q6："Docker Compose 里的 healthcheck 是做什么的？"
> "`depends_on` 默认只等容器启动，不等服务就绪。如果 PostgreSQL 容器启动了但数据库还没准备好，app 容器连不上就崩了。`healthcheck` + `condition: service_healthy` 保证 app 启动时 PostgreSQL 已经可以接收连接。这是容器编排的基本功。"
